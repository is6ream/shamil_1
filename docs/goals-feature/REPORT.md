Ветка `feature/fundraising-goals` (от `origin/production` @ 97d2547), worktree `.worktrees/goals`.
Пять локальных коммитов, **ничего не запушено**, прод, продовая база, S3 и `.env` продакшена не трогались.

## 1. Что сделано

**Главная.** На первом экране под «Собрано» — стеклянная карточка «Текущий этап: На кирпичи»: тонкая полоса,
«Собрано 245 000 ₽ из 700 000 ₽ · 35%», кнопка «Помочь» (прокрутка к форме и фокус), подпись
«Все пожертвования направляются на строительство мечети «Шамиль». Оферта». Цифры — из базы.
Анимация: полоса `scaleX` и счётчик суммы одной кривой за 1,2 с при появлении на экране, бегущий блик,
свечение края; `prefers-reduced-motion` — сразу итог. Цель достигнута — плашка «Цель достигнута, спасибо!»,
этап сам не завершается. Нет активного этапа или API недоступен — блок не рисуется, страница работает.

**Кабинет**, раздел «Цели сбора» → новая секция «Этапы сбора на главной»: таблица (название, цель,
собрано с разбивкой «сайт · вручную», %, статус, период; активный выделен), форма в рублях с живым превью
блока главной, «Сделать активным» с подтверждением «Текущий этап «…» будет завершён», «Завершить»,
«В архив», поле ручной корректировки с подсказкой про QR СБП, наличные и переводы по реквизитам.

**API.** `GET /api/public/goals/active` (без авторизации, кеш 30 с, лимит 120/мин) и `/api/admin/goals`:
список с прогрессом и пагинацией, создание, правка, `activate` / `complete` / `archive`. Удаления нет.
«Собрано» считает `GoalProgressCalculator` одним агрегирующим SQL. Контракт — [docs/admin/API.md §14а, §16, §17](../admin/API.md).

**БД.** Аддитивная миграция `20261022120000_fundraising_goals`: enum, таблица `fundraising_goal`,
CHECK-ограничения, частичный уникальный индекс «активный этап один», триггеры статуса и запрета удаления.

## 4. Чек-лист выкладки в production

### Переменные окружения

### Миграция

- Применится **автоматически при старте контейнера API**: `CMD` в `Dockerfile` — `npx prisma migrate deploy && … node dist/main.js`.
- **Строго аддитивная:** `CREATE TYPE`, `CREATE TABLE fundraising_goal`, его индексы, CHECK, FK
  (на `campaign` и `admin_user`), функция и два триггера **на новой таблице**. `ALTER` существующих таблиц нет,
  данных пожертвований не касается, новых индексов на `donation` нет. Блокировки — только на новую таблицу.
- Prisma-объявление обратных связей в `Campaign`/`AdminUser` колонок не добавляет (проверено `migrate diff`).

### Порядок

1. **Backend** (с миграцией). Проверить `GET https://api.mechetshamil.ru/api/public/goals/active` → 200, пустое тело.
2. **Frontend.**

Если фронт выйдет раньше: `GET /public/goals/active` вернёт 404, `withFallback` его поймает — блок не рисуется,
главная работает, в логе сайта при каждой перегенерации строка «[витрина] «активный этап сбора» недоступно».
Если бэкенд с новым кодом раньше, а фронт старый: при правке этапа API шлёт тег `active-goal`, старый фронт
ответит 400 — API запишет `warn`, сохранение пройдёт. Оба порядка безопасны, правильный — backend → frontend.

### Откат

1. Фронт: откатить на предыдущий коммит `production` — блок исчезнет, остальное без изменений.
2. Бэкенд: откатить код. **Миграцию не откатывать** — пустая/неиспользуемая таблица ничему не мешает.
   Проверено локально: `prisma migrate deploy` старой версии на базе с новой миграцией завершается успешно
   («No pending migrations», exit 0) — контейнер стартует.
3. Если таблицу всё же нужно убрать (не требуется): вручную `DROP TABLE fundraising_goal; DROP FUNCTION
   fundraising_goal_status_guard(); DROP TYPE fundraising_goal_status;` и удалить строку миграции
   из `_prisma_migrations` — только после бэкапа и только когда код без этапов уже на проде.

## 5. Найдено по пути в соседнем коде (не исправлялось, вне задачи)

1. **SSR-запросы к API без таймаута** — `apps/web/lib/api/client.ts`, `send()` вызывает `fetch` без `AbortSignal`.
   Если API «зависнет» (принимает соединение и не отвечает), перегенерация главной будет ждать до таймаута
   платформы; `withFallback` спасает только от ошибки, не от ожидания. Стоит `AbortSignal.timeout(…)` для `apiGet`.
2. **Общая сумма сбора не видит корректировок этапов** — «Собрано 0 ₽ из 240 млн» рядом с этапом
   «245 000 ₽» на демо-данных. Это следствие ТЗ (корректировка — поле этапа), но на проде лучше вносить
   поступления по QR как ручные пожертвования: тогда растут и этап, и общий сбор, и рейтинги.
3. **`isExclusionViolation` ищет код ошибки в тексте сообщения** (`database/prisma-errors.ts`) — хрупко
   к смене формата сообщений Prisma; то же вынужденно сделано и для частичного индекса здесь
   (`isActiveIndexViolation`), но там подстраховано `P2002`.
4. **Троттлинг в памяти процесса** (`ThrottlerModule` без внешнего хранилища): лимиты обнуляются при
   рестарте и делятся на инстансы, если их станет больше одного; лимит входа в админку при этом ослабнет.
5. **Фокус «Помочь»/нижней плашки на QR-вкладке** — был дефект: фокус оставался на кнопке. **Исправлен**
   в рамках задачи (кнопка «Помочь» этапа требует фокус в форме), см. DECISIONS D17.
6. **Prisma пишет ошибки БД в консоль** (`log: ['warn', 'error']`: место вызова и текст ошибки PostgreSQL) —
   на проде это уходит в логи App Platform. В ошибках этапов ПДн нет; для `donation_contact` стоит проверить,
   не попадают ли значения (телефон) в текст нарушений ограничений.
