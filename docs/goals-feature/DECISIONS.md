# Этапы сбора — принятые решения

Каждое решение: что выбрано, почему, какие были альтернативы.

## D1. Базовая ветка — `origin/production`, работа в отдельном worktree

- **Выбрано:** `feature/fundraising-goals` от `origin/production` (97d2547), worktree `.worktrees/goals`.
- **Почему:** `main` отстал (08.10), а в `production` — актуальная главная (новая форма, QR СБП, оферта, UTM).
  Основная папка занята веткой `feature/lk-ui-ux-redesign` с чужими незакоммиченными правками — переключать
  её нельзя.
- **Альтернативы:** `main` (устарел), `feature/lk-ui-ux-redesign` (там редизайн кабинета, но старая главная
  и нет оферты). **Следствие:** раздел кабинета сделан в текущем стиле production-кабинета. При слиянии
  с редизайном ЛК (`feature/lk-ui-ux`, на 22.10 ещё не в production) секция переедет на его токены.
  Проверено `git diff`: из файлов этой задачи редизайн переписывает `components/admin/ui/DataTable.tsx` —
  там будет конфликт (здесь добавлен один необязательный проп `rowClassName`, его нужно перенести);
  `app/admin/(panel)/goals/page.tsx` редизайн не трогает.

## D2. Отдельная локальная база

`shamil_goals` и `shamil_goals_test` на том же контейнере `shamil-postgres` (5434). Тесты других сессий
TRUNCATE-ят `shamil_test` — общая база дала бы ложные падения в обе стороны.

## D3. Имена полей ответа — с суффиксом `Kopecks`

- **Выбрано:** `targetAmountKopecks`, `collectedAmountKopecks` вместо `targetAmount`, `collectedAmount` из ТЗ.
- **Почему:** ТЗ просит «в формате, единообразном с остальным API»; во всём API деньги — строки копеек
  с суффиксом (`goalKopecks`, `collectedKopecks`, `paidAmountKopecks`). Число вместо строки потеряло бы
  точность на больших суммах.

## D4. Путь публичного эндпоинта — как в ТЗ: `GET /api/public/goals/active`

Остальная витрина живёт без префикса `public` (`/api/campaign`), но путь из ТЗ явный и ничему не мешает.
Нет активного этапа — **200 с пустым телом** (так Nest отдаёт `null`); фронт трактует это как «этапа нет».

## D5. Этап привязан к сбору (`campaign_id`)

В формуле ТЗ сбора нет, но донаты принадлежат сбору, и цели месяца тоже считаются по сбору. Без привязки
второй сбор (в схеме это предусмотрено) смешался бы с этапами первого. Этап создаётся в сборе `CAMPAIGN_SLUG`.

## D6. Порядок значений enum: `ACTIVE, DRAFT, COMPLETED, ARCHIVED`

Prisma сортирует enum по порядку в базе; так `ORDER BY status` ставит активный этап первым без
выражений в `ORDER BY`. На API это не влияет — значения те же, что в ТЗ.

## D7. Переходы статусов

- `DRAFT → ACTIVE`, `ACTIVE → COMPLETED`, **`COMPLETED → ACTIVE`** (вернуть по ошибке завершённый),
  любой не-архивный → `ARCHIVED`. `ARCHIVED` финален и не редактируется. В `DRAFT` не возвращаются.
- Проверяет сервис (409 с понятным текстом) **и** триггер БД `fundraising_goal_status_guard_bu` —
  как у донатов: писать в таблицу можно не только через сервис.
- `DELETE` запрещён триггером `…_bd` — «физического удаления нет» и на уровне базы.
- **Альтернатива:** архив только из `COMPLETED` — лишний шаг для админа без выигрыша в безопасности.

## D8. «Активный один» и гонка активаций

- Частичный уникальный индекс `fundraising_goal_single_active ON (status) WHERE status = 'ACTIVE'`.
- Активация: `SELECT … FOR UPDATE` строки этапа → `UPDATE` текущего активного в `COMPLETED`
  (`WHERE status = 'ACTIVE'`, перепроверяется после ожидания блокировки) → `UPDATE` нового в `ACTIVE`,
  всё в одной транзакции. Параллельная транзакция, которая уже включила другой этап, приводит к 23505
  на индексе → `ConflictException` (409). Проверено детерминированным тестом с удержанием транзакции.

## D9. Окно «собрано» у завершённого этапа закрывается моментом завершения

- **Выбрано:** конец окна = `LEAST(ends_at, completed_at)` (NULL игнорируется).
- **Почему:** при ручной проверке «На кирпичи» без даты окончания после завершения продолжал копить
  пожертвования, которые уже шли в следующий этап, — в таблице кабинета у двух этапов росли одни и те же деньги.
  Для активного этапа формула совпадает с ТЗ (`completed_at` у него всегда NULL — активация его стирает).
- **Альтернатива:** формула ТЗ буквально — историческая цифра завершённого этапа «плывёт».

## D10. Кеш публичного эндпоинта — 30 с в памяти процесса, промис в кеше

Пачка одновременных запросов после истечения делает один запрос в базу; упавший запрос из кеша убирается
сразу. Любая правка этапа сбрасывает кеш. На App Platform у API один инстанс; при нескольких инстансах
остальные догонят за 30 с — записано в комментарии `ActiveGoalService`.

## D11. Троттлинг публичного эндпоинта — свой лимит 120/мин на IP

Остальная витрина под `@SkipThrottle` (SSR с одного IP). Здесь сайт ходит через ISR раз в 60 с, поэтому
лимит не мешает сайту, а перебор режет. При 429 сайт просто не покажет блок (`withFallback`).

## D12. Ревалидация: тег `active-goal` — только когда правка видна на сайте

Шлётся при правке активного этапа, активации, завершении и архиве активного. Создание черновика и правка
неактивного сайт не трогают. Вызов не ждётся; сбой логирует `RevalidationService` (`warn`), сохранение
не откатывается — это существующий механизм проекта, переиспользован без изменений.

## D13. Формат сумм на главной — `Intl.NumberFormat('ru-RU', RUB)` + нормализация пробелов

ТЗ требует `Intl`. В проекте от него сознательно уходили: ICU Node и браузера расходятся разделителем
(обычный / U+202F / U+00A0) — hydration mismatch. Решение: результат `Intl` прогоняется через замену
любого пробела на U+00A0 — строка одинакова на сервере и в браузере, знак ₽ не отрывается от числа.

## D14. Анимация — один цикл rAF для полосы и счётчика, запись в DOM напрямую

- Серверный HTML содержит итог (без JS всё верно). При первом появлении во viewport rAF ведёт полосу
  (`transform: scaleX`) и сумму по одной кривой `easeOutCubic` 1,2 с; React-состояние не меняется
  (нет 70 перерисовок за анимацию).
- Свечение края — отдельный слой с `translateX`: внутри `scaleX` точка растянулась бы.
- `prefers-reduced-motion: reduce` — rAF не запускается, блик и свечение выключены CSS.
- Без новых зависимостей.

## D15. Место блока: под «Собрано» в hero

Десктоп: левая колонка, форма справа не сдвигается (проверено 1440×900: низ формы на 729 px из 900).
Телефон: последним перед формой (CSS `order: 3`), описание скрыто. Блок сдвигает форму вниз на ~183 px —
но форма на телефоне и до изменения начиналась ниже первого экрана (hero идёт первым), а требование
«форма целиком помещается на экран» про высоту карточки, и оно выполняется: 384 ≤ 640, 536 ≤ 844.

## D16. Раздел кабинета — секция внутри существующих «Цели сбора»

Не новый пункт меню: у владельцев уже есть «Цели сбора», и три вида целей в одном месте понятнее.
Живое превью — тот же компонент `GoalProgress`, что на главной (режим `isPreview`: без анимации,
кнопка и ссылка неактивны), на тёмной подложке, как на первом экране.

## D17. Фокус после «Помочь», когда форма открыта на QR

`scrollToSection` ставил фокус только на поле суммы, а в manual-режиме форма открыта на вкладке QR — полей
суммы нет, фокус оставался на кнопке (то же было у нижней плашки телефона). Добавлен запасной селектор:
первый доступный контрол формы. Правка в общем хелпере, затрагивает и шапку, и плашку — в лучшую сторону.

## D18. Демо-этап только при `NODE_ENV === 'development'`

Сиды запускаются и на проде (`RUN_SEED=true`). Условие — явное `development`, а не «не production»:
пустой или неизвестный `NODE_ENV` тоже ничего не создаёт. Создаётся, только если этапов нет вовсе.

## D19. Новых переменных окружения нет

Используются существующие `REVALIDATE_SECRET` (API и сайт, ≥ 32 символа) и `WEB_REVALIDATE_URL`
(по умолчанию `${PUBLIC_SITE_URL}/api/revalidate`). `.env.example` не менялся — добавлять нечего.

## D20. Зависимости не добавлялись

Всё на имеющихся: Nest, Prisma, class-validator, Next, React. Playwright (уже в devDependencies корня)
использован только для ручной проверки, скрипт в репозиторий не добавлен.
