## 2. Найденные проблемы и исправления

| Проблема | Исправление |
| --- | --- |
| Переключение на `manual` отключало также проверку старых callback | Отдельный `PAYMENT_ONLINE_ORDERS_ENABLED=false`; Robokassa и ключи остаются включены |
| Параллельные разные события могли прочитать одинаковый старый статус | Блокировка строки заказа `FOR UPDATE` внутри транзакции до чтения статуса |
| В подпись передавалась проверенная сумма из переменной запроса | Подписывается `amountKopecks`, возвращённая БД после сохранения заказа |
| Массив `Shp_*` исключался из подписи как отсутствующее значение | Такой callback отклоняется до разбора и сохранения |
| Production stage при ошибочном NODE_ENV не включал все платёжные запреты | `DEPLOY_STAGE=production` самостоятельно включает запрет эмулятора и чужого платёжного URL |
| Экран без номера заказа обещал, что платёж учтён; failed обещал отсутствие списания | Тексты сообщают только проверенное состояние; поздний paid можно запросить повторно |
| Зависший HTTP-запрос статуса мог бесконечно удерживать экран проверки | Таймаут запроса статуса 10 секунд; ошибка не подтверждает и не отклоняет платёж |
| Ошибка типов обёртки Web Locks мешала отдельному web typecheck | Асинхронная обёртка сохраняет общий refresh-lock и корректный тип результата |

Сохранено: деньги — целые копейки/bigint; `InvId=invoiceNo`, UUID в `Shp_order_id`;
подпись исходного `OutSum` и всех фактических строковых `Shp_*` проверяется до записи;
`100.000000` разбирается без float. Событие и изменение заказа атомарны,
идемпотентность обеспечена уникальным `(provider, provider_event_id)`;
`paid` финален, `failed → paid` разрешён. Витрины пересчитывают существующие SQL-триггеры.
Ручное подтверждение защищено JWT/ролью либо токеном по D-07 и разрешено только manual.

D-03 сохраняется: подписанное расхождение зачисляется по факту, с warn и
`donation.amount_mismatch` в audit после зачисления. Ошибка audit логируется отдельно
и не откатывает деньги. Неизвестный подписанный счёт сохраняется без привязки к донату;
OK допустим после надёжной записи этого события. При сбое БД OK не возвращается.

**Противоречия:** старые документы называют минимум 100 ₽; текущие DTO, код и миграция
`20261027150000_min_donation_10_rub` — 10 ₽. Текущее поведение оставлено до решения владельца.
Receipt остаётся выключенным по решению проекта; это не независимое юридическое заключение.
Тариф и необходимость фискализации владелец подтверждает с бухгалтером/Robokassa.

## 6. Robokassa: протокол и кабинет

Сверено 03.11.2026 с официальными разделами
[интерфейс оплаты](https://docs.robokassa.ru/ru/pay-interface),
[уведомления](https://docs.robokassa.ru/ru/notifications-and-redirects) и
[тестовый режим](https://docs.robokassa.ru/ru/testing-mode).
ResultURL подтверждает оплату серверу; SuccessURL только возвращает посетителя.
При проверенной подписи и надёжной обработке сервер возвращает `OK{InvId}`.
Шесть дробных знаков OutSum в рабочем режиме учитываются как исходная строка.
Тестовый режим использует отдельную пару паролей и `IsTest=1`.
Документация сейчас допускает InvId до int64; локальная схема использует int4 —
её более узкая граница сохранена, расширение схемы для запуска не требуется.

Адреса для подтверждения владельцем в технических настройках магазина:

| Поле | Адрес | Метод |
| --- | --- | --- |
| Result URL | `https://api.mechetshamil.ru/api/payments/robokassa/result` | POST |
| Success URL | `https://mechetshamil.ru/spasibo` | GET |
| Fail URL | `https://mechetshamil.ru/` | GET |

Дополнительные ResultUrl2/SuccessUrl2 не используются. Редирект Fail не меняет
статус заказа; отсутствие callback оставляет pending. Для тестового магазина
использовать адреса отдельного тестового web/API, не перечисленные production URL.

Форма обещает СБП, карту, SberPay и T-Pay. Она передаёт канал online, а конкретный
способ выбирается в Robokassa; выбор плитки не фиксирует способ в ссылке оплаты.
Наличие всех способов у конкретного магазина **не проверено**. До включения
подтвердить их в кабинете и на странице оплаты, а также обещание «комиссия включена».
Если способ недоступен, запуск блокируется до согласованного изменения списка/текста.
Сырые PaymentMethod/IncCurrLabel сохраняются; не придумывать соответствия для ленты.
Production сохраняет переключатель «По QR-коду / Через форму» и его исходный режим QR.
Флаг API не переключает интерфейс: перед запуском проверить реальный QR/получателя
и доступность онлайн-оплаты через вкладку «Через форму».

## 8. Порядок выпуска после отдельного согласования

1. Повторно проверить production SHA и выбранный diff. При изменении базы пересобрать
   кандидат и повторить проверки. Не публиковать WIP целиком.
2. Проверить свежую резервную копию БД, срок хранения и ответственного. Выполнить
   пробное восстановление в отдельную БД: таблицы, контрольные суммы paid/count,
   миграции и SQL-триггеры должны совпасть с моментом бэкапа. Зафиксировать время восстановления.
3. В выбранном выпуске не удалять production-миграции. Сравнить `_prisma_migrations`
   и каталог миграций; использовать `prisma migrate status`, затем штатный
   `npm run db:migrate:deploy --workspace @shamil/api`. Не использовать reset/db push
   и не запускать seed для проверки. Учитывать автоматический migrate deploy в Dockerfile.
4. Развернуть backend с реальными ключами, `PAYMENT_IS_TEST=false`, эмулятором off
   и новыми заказами off. Проверить health/ready, HTTPS, CORS, защищённость админки,
   ResultURL и старые уведомления. На неподписанный callback ожидается 401 без записи.
5. Развернуть frontend с правильным API URL, проверить отсутствие fallback-цифр,
   доступность реквизитов и документов, создание заказа только после включения.
6. После допуска магазина и отдельного согласования включить новые онлайн-заказы.
   Владелец сам выполняет первый контрольный реальный платёж; агент списание не делает.
7. Зафиксировать новый SHA/версии deployment и время выпуска в этом документе.

Откат приложения — на зафиксированный предыдущий артефакт, совместимый со схемой.
Откат к версии без нового флага снова разрешит заказы: до такого отката отдельно
закрыть только создание online-заказов на ingress, сохраняя ResultURL и чтение статусов.
Не восстанавливать production-БД поверх поздних оплат без отдельного плана сверки и
повторного применения уведомлений: иначе реальные поступления будут потеряны из учёта.

## 9. Остановка новых оплат и контрольный платёж

Аварийная остановка: установить `PAYMENT_ONLINE_ORDERS_ENABLED=false` на всех API-инстансах
и штатно перезапустить/перевыпустить их. Сохранить `PAYMENT_PROVIDER=robokassa`, домен
ResultURL, режим и ключи. Transfer и подтверждение manual продолжают работать.
Новые запросы online получают ошибку до создания заказа; уже выданные ссылки могут
быть оплачены и должны получить callback. Флаг не отменяет существующие счета.
Не выключать API и не заменять провайдер на manual ради остановки новых оплат.

Первый реальный контроль выполняет владелец после допуска: выбрать согласованную
малую сумму не ниже текущих 10 ₽, сохранить order UUID и invoice, оплатить один раз.
Проверить в кабинете факт оплаты, в БД — один применённый payment_event, paid и
фактическую сумму, в админке — тот же донат, в витринах — ровно одно увеличение.
