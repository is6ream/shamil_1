## 1. ORM: Prisma

Взята Prisma 7 — с ней быстрее всего пройти дни 6–9, а не потому что она «лучше вообще».

| Что решает | Как |
| --- | --- |
| Типы моделей без дублирования | `prisma generate` отдаёт типы прямо из схемы; DTO пишутся один раз |
| Миграции — обычный SQL | `prisma/migrations/*/migration.sql` можно читать, править и дописывать руками |
| Деньги | `BigInt` ↔ `bigint` один в один, без промежуточных `number` |
| Keyset-пагинация | Обычный `where` + `orderBy`, без обхода ORM |

**Чего Prisma не умеет** — и почему это не заблокировало выбор: CHECK-ограничения,
триггеры, EXCLUDE и частичные индексы в `schema.prisma` не описываются. Они лежат
отдельной миграцией обычным SQL. Проверено: `prisma migrate dev` их **не видит и не
удаляет** — сгенерированная после них миграция вышла пустой. Сохранность объектов
всё равно закреплена тестом `schema-guards.spec.ts`, потому что цена ошибки —
разъехавшаяся сумма сбора.

Prisma 7 работает через драйвер-адаптер (`@prisma/adapter-pg`), строка подключения
идёт из провалидированного конфига приложения, а не из `schema.prisma`.
Побочный эффект: CLI больше не читает `.env` сам — его грузит `prisma.config.ts`.

Альтернативы (Drizzle, Kysely, TypeORM) не рассматривались всерьёз: при 32 часах на
проект решает не выразительность ORM, а количество кода, который не нужно писать.

## 2. Таблицы

Четыре сущности из роудмапа — `campaign`, `donation`, `region`, `gallery_item` — плюс
пять служебных. Каждая добавленная закрывает требование, которое иначе пришлось бы
чинить миграцией по живому.

| Таблица | Зачем |
| --- | --- |
| `campaign` | Сбор: общая цель, валюта учёта, минимальный донат |
| `campaign_monthly_goal` | Цель на месяц **с границами периода** — верхняя шкала прогресс-бара |
| `campaign_stats` | Витрина сбора: собрано, число платежей, время последнего |
| `region` | Справочник «откуда вы»: страны и субъекты РФ |
| `region_stats` | Витрина рейтинга землячеств |
| `donation` | Донат |
| `donation_contact` | ПДн донатера: телефон, имя, согласие (152-ФЗ) |
| `payment_event` | Колбэки провайдера; ключ идемпотентности |
| `gallery_item` | Фотогалерея стройки |

### Почему цель месяца — таблица, а не колонка

«Цель на месяц» без границ периода не считается: непонятно, какие донаты в неё входят.
Колонка в `campaign` означала бы, что каждый новый месяц затирает предыдущий, и первый
же вопрос заказчика «а сколько собрали в сентябре» остаётся без ответа. Отдельная
таблица даёт историю, а EXCLUDE-ограничение не даёт периодам пересечься — иначе один
донат попал бы в две шкалы.

### Почему ПДн отдельно

Телефон в `donation_contact`, а не в `donation`. Два следствия, оба нужны:

- публичные выборки (живая лента, топы, рейтинг) читают `donation` и физически не могут
  вытащить телефон — забыть исключить поле в новом эндпоинте не получится;
- по требованию об удалении ПДн строка удаляется, а донат и сумма сбора остаются.
  Проверено тестом.

Публичная подпись донатера (`donation.donor_name`) и имя для сверки платежей
(`donation_contact.full_name`) — **разные поля**. У анонимного доната публичная подпись
запрещена CHECK-ом: чего в таблице нет, то невозможно показать по ошибке.

### Почему события платежей — отдельная таблица

`provider_event_id` можно было положить колонкой в `donation`, но у одного доната
событий несколько (создание, успех, возможный возврат), а разбирать спорный платёж без
сырого тела колбэка нечем. Уникальный `(provider, provider_event_id)` — это и есть
идемпотентность: повторная доставка упирается в индекс, донат не задваивается.

Если провайдер своего id события не даёт (Robokassa присылает только номер счёта),
в это поле кладётся детерминированный хеш тела — повтор даёт тот же ключ.

## 3. Инварианты, вынесенные в БД

Всё ниже — вторая миграция (`…_guards_and_stats`) и третья (`…_stats_apply_without_upsert`).
В `donation` пишут три пути: вебхук, админский ручной донат и сиды. Правило, живущее
только в сервисе, рано или поздно обойдут — поэтому оно в базе.

### pending → paid, и никогда обратно

Триггер `donation_status_guard`:

- `paid` → любой другой статус — ошибка `DONATION_PAID_IS_FINAL`;
- возврат в `pending` из любого статуса — `DONATION_NO_RETURN_TO_PENDING`;
- удаление оплаченного доната — `DONATION_PAID_DELETE_FORBIDDEN` (по нему посчитаны
  сумма сбора и рейтинг);
- повтор того же статуса проходит как no-op: ретрай вебхука — не ошибка.

`failed → paid` **разрешён**: отказной колбэк может прийти раньше успешного, и в этом
случае деньги важнее порядка доставки. Зеркало этих правил для сервиса —
`src/donations/donation-status.ts`.

### Деньги

- все суммы — `bigint` в копейках; тест проверяет, что ни одна денежная колонка
  не уехала в `numeric` или `double precision`;
- `amount_kopecks` — сумма заказа, сформированная сервером;
  `paid_amount_kopecks` — фактически оплаченная, из вебхука. В витрины идёт только вторая;
- `paid` обязан нести и время, и фактическую сумму; в остальных статусах следов оплаты
  быть не должно (CHECK `donation_paid_fields`);
- минимум 100 ₽ — продуктовое правило, оно в DTO. В БД только «сумма больше нуля»:
  перевод по реквизитам на 50 ₽ админ обязан иметь возможность внести.

### Валюта платежа

Учёт ведётся в копейках рубля. Для Kaspi (KZT) и Mbank (KGS) в `donation` оставлены
`charged_currency` и `charged_amount_minor` — фактическое списание. Как именно придёт
курс, станет ясно, когда заказчик подтвердит провайдеров; место под это уже есть,
мигрировать боевую таблицу не придётся.

### Витринные счётчики

Пересчитываются триггером `donation_stats_sync` при каждом переходе в `paid` и при
правке оплаченного доната (смена региона, исправление суммы, сдвиг даты): старый вклад
снимается целиком, новый начисляется. Разбирать, что именно изменилось, не нужно.

Месяц определяется по московскому времени, а не по таймзоне сервера — иначе донат
в 23:30 31-го числа попадёт в разные месяцы на разных машинах.

Строка счётчиков появляется сразу при создании сбора или региона, с нулями. Поэтому
«ещё N регионов ждут первого пожертвования» — обычный SELECT, а не вычисление разницы.

> **Грабли, на которые уже наступили.** Дельта начислялась через
> `INSERT … ON CONFLICT DO UPDATE`. PostgreSQL проверяет CHECK на предложенной строке
> **до** обнаружения конфликта, а при вычитании она отрицательная — падало
> «paid_total_kopecks >= 0». Починено третьей миграцией: строка создаётся отдельным
> INSERT с нулями, дельта применяется UPDATE.

### Справочник регионов

- страна — корень, субъект — лист с официальным кодом; смешанные варианты запрещены
  CHECK-ом `region_hierarchy`;
- одна страна — одна строка (частичный уникальный индекс: `(country_code, code)`
  для стран не работает, там `code` пуст, а NULL сам с собой не конфликтует);
- `donation.region_id` — **nullable**, и это проверено тестом: донат без региона обязан
  проходить. Платёж важнее статистики;
- `region_id` и `region_source` записываются только вместе. Источник атрибуции
  (`link` — региональная ссылка, `form` — селектор, `admin`) нужен, чтобы увидеть
  провал атрибуции раньше, чем он станет 93%, как у референса.

## 4. Индексы под конкретные экраны

| Индекс | Экран |
| --- | --- |
| `donation (status, paid_at DESC, id DESC)` | Живая лента: keyset-курсор по `(paid_at, id)`, без OFFSET |
| `donation (status, is_anonymous, paid_amount_kopecks DESC)` | Топ донатеров — только снявшие анонимность |
| `region_stats (paid_total_kopecks DESC)` | Топ регионов |
| `region (type, sort_order, name)` | Селектор «откуда вы» |
| `gallery_item (campaign_id, is_published, sort_order, taken_on)` | Галерея в хронологии стройки |
| `donation (recurring_id)` | Автоплатёж, когда до него дойдёт дело |

Запрос ленты, который пойдёт в API дня 6, зафиксирован тестом — страницы не пересекаются
и не теряют строк при вставке новых донатов между запросами. Это то, чем keyset лучше
OFFSET, ради чего он и выбран.

## 5. Сиды

`npm run db:seed --workspace @shamil/api` (на проде — `node dist/database/seed/index.js`,
без dev-зависимостей).

Создаётся: 3 страны (Россия, Казахстан, Кыргызстан), 85 субъектов РФ, сбор с целью
240 000 000 ₽, цель месяца. Донатов и фотографий сиды не создают — в публичном сборе
не должно быть придуманных цифр.

Сиды идемпотентны: повторный запуск обновляет названия из справочника и цель из ТЗ,
но **не перетирает** то, что могли поправить руками — цель месяца, минимальный донат,
флаги и порядок регионов.

### Состав списка регионов

85 субъектов, как в справочнике референса. Коды — те, что люди знают по автомобильным
номерам (`02` — Башкортостан, `95` — Чечня): их диктуют голосом, когда делятся
региональной ссылкой `/{код}/`. Территории, вошедшие в состав РФ после 2022 года,
в список не включены — добавлять ли их, решает заказчик.

Башкортостан стоит первым (домашний регион), затем Казахстан и Кыргызстан, дальше
остальные по алфавиту.

**«Россия» в рейтинге не участвует** (`is_ranked = false`): она родитель 85 строк
и всегда была бы первой, а соревнование землячеств при этом рассыпается. В форме
выбрать её можно — донатер вправе не называть регион точнее. Переключается одним
UPDATE, если заказчик решит иначе.

## 6. Тесты

`npm run test --workspace @shamil/api` — 52 теста, из них 40 работают с настоящим
PostgreSQL. Проверять триггеры и CHECK моками бессмысленно: проверять тогда нечего.

| Файл | Что проверяет |
| --- | --- |
| `donations/donation-status.spec.ts` | Правила переходов в коде (без БД) |
| `database/donation-lifecycle.spec.ts` | Переходы статуса, запрет удаления, CHECK-и, удаление ПДн |
| `database/webhook-idempotency.spec.ts` | Повторная доставка колбэка не задваивает сумму сбора |
| `database/showcase-stats.spec.ts` | Витрины, цель месяца, донат без региона, keyset-лента |
| `database/schema-guards.spec.ts` | Триггеры, CHECK, EXCLUDE и `bigint` на месте |

Тестовая база создаётся сама и получает миграции перед прогоном — ручных шагов нет.
Если сервер БД недоступен, тесты на схему **пропускаются с предупреждением**, а не
падают: без базы они бессмысленны, но остальной набор должен оставаться зелёным.
Адрес — `TEST_DATABASE_URL` в `.env`, отдельная база: тесты очищают таблицы целиком.

Прогон последовательный (`maxWorkers: 1`): параллельные файлы ловят deadlock
на TRUNCATE одной и той же базы. При таком размере набора это дешевле изоляции по схемам.

## 7. Что осталось решить заказчику

Ничего из этого не блокирует дни 6–9: схема готова под оба варианта ответа. Но чем
позже ответ, тем дороже правка.

- **Валюта цели** 240 000 000 — рубли? Учёт уже ведётся в копейках рубля.
- **Цель на месяц** — конкретная сумма и период. Сейчас в сидах заглушка 5 000 000 ₽
  на текущий месяц, и она выводится предупреждением при каждом запуске.
- **Минимальный донат** 100 ₽ — подтверждаем? Заложен в `campaign.min_donation_kopecks`,
  меняется без миграции.
- **Показывать ли «Россию» строкой рейтинга** рядом с субъектами.
- **Территории, вошедшие в состав РФ после 2022 года** — включать в справочник?
- **Флаги и гербы регионов** — откуда берём изображения (`region.flag_url` пока пуст).
- **Топ донатеров: по одному платежу или по сумме от человека?** Личного кабинета нет,
  единственный надёжный ключ человека — телефон, а он в таблице ПДн. От ответа зависит
  запрос дня 6, не схема.

## 8. Команды

```bash
npm run db:up                                    # PostgreSQL в Docker (из корня)
npm run db:migrate --workspace @shamil/api       # создать миграцию по изменённой схеме
npm run db:migrate:deploy --workspace @shamil/api # применить миграции (прод)
npm run db:seed --workspace @shamil/api          # справочные данные
npm run db:studio --workspace @shamil/api        # посмотреть данные глазами
npm run test --workspace @shamil/api             # тесты, включая тесты схемы
```

При генерации новой миграции — открыть её и убедиться, что она не удаляет ничего
из второй и третьей: триггеры, CHECK и EXCLUDE Prisma в `schema.prisma` не описывает.
