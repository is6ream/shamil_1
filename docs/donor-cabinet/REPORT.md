# Кабинет пожертвователя и регулярная помощь

Кандидат в рабочей копии `donor-full`, ветка `feature/donor-cabinet-full`. База для сверки выпуска — удалённая `production` на `7ad9ce9` по состоянию на 4 ноября 2026 года. Версию работающих приложений Timeweb нужно проверить отдельно.

## Миграции

- До обновления существующей БД сверить `_prisma_migrations` и резервную копию. Уточнить, встречается ли старое имя `20261027100000_donor_cabinet_sessions_profile`, в том числе с незавершённым применением. При наличии такой записи сначала определить фактическое состояние схемы и согласовать её выравнивание.
- Проверенный порядок на PostgreSQL 18 — `20261028100000_donor_cabinet_subscriptions`, `20261028110000_donor_cabinet_sessions_profile`, `20261104100000_subscription_period`. Проверены чистая установка и обновление с первых 17 миграций. Новая колонка получает `MONTHLY` по умолчанию, новая форма предлагает пятницу.
- Перед выпуском проверить восстановление из резервной копии. При откате приложения отдельно учитывать миграцию сессий и профиля. До допуска схемы проверять предыдущую версию API на обновлённой тестовой БД.

## Проверка на локальном стенде

- Прошли 815 API-тестов в 62 наборах на отдельной PostgreSQL без пропусков, повторно 53 затронутых API-теста, 225 web-тестов, typecheck, lint и production-сборки API и web.

- PostgreSQL 18. Миграции применились к чистой базе и к схеме с существующей подпиской на 100 ₽. После обновления сумма сохранилась, период стал `MONTHLY`.
- Браузер Edge. Десктоп 1440×900 и эмуляция iPhone 13. Проверены вход с кодом из тестового журнала, профиль, история, разовое пожертвование, первая оплата месячной и пятничной подписок, изменение суммы, пауза и возобновление.
- Для проверки повторных платежей время следующего списания сдвигалось в локальной БД. Оба платежа обработал планировщик через HTTP-эмулятор Robokassa. Повторные Result URL для разового и дочерних платежей дали по одному применённому событию на счёт.
- Проверена отмена в кабинете и через ссылку из тестового письма в анонимной вкладке. Открытие ссылки оставляло подписку активной до нажатия кнопки подтверждения.
- Проверка нашла расхождение времени в PostgreSQL с часовым поясом `UTC+05`. Соединения Prisma теперь используют UTC, а календарь рассчитывает даты по часовому поясу жертвователя.

## Последовательность выпуска

1. Сверить целевые версии API и web, настройки CORS, cookie, SMTP и существующий Result URL. Согласовать публикуемые условия регулярного пожертвования и минимальную сумму с владельцем.
2. После одобрения обновить схему, выпустить API и проверить `/api/health`, подключение к БД, `SHOW TIME ZONE` через соединение приложения и существующие платежные маршруты. Для выпуска кабинета включить `DONOR_CABINET_ENABLED` на API и собрать web с `NEXT_PUBLIC_DONOR_CABINET_ENABLED`. Проверить фактическую доставку почты и отдельно прогнать VK ID при настроенном приложении.
3. До подтверждения рекуррентов держать `RECURRING_ENABLED`, `NEXT_PUBLIC_RECURRING_ENABLED` и `BILLING_SCHEDULER_ENABLED` выключенными. После подтверждения услуги и согласования с владельцем проверить договорённый с Robokassa порядок проверки, параметры первого платежа, Result URL и сверку дочерней операции через OpStateExt. Только после отдельного допуска включать расписание и оформление.
4. Для аварийной остановки рекуррентов выключить `RECURRING_ENABLED` и планировщик на API и убрать форму в следующей web-сборке. Оставить доступ к управлению подписками и обработку уведомлений для уже выставленных счетов. Проверить платежи, которые уже были переданы провайдеру.

[Протокол рекуррентных платежей Robokassa](https://docs.robokassa.ru/ru/recurring-payments) и [ограничения тестового режима Merchant/Recurring](https://mcp.robokassa.ru/).
