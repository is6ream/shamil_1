## 2. Переменные Timeweb App Platform

### Фронт — на этапе **сборки**

`NEXT_PUBLIC_*` вшиваются в бандл при `next build`. После изменения — **пересобрать** фронт,
простого перезапуска мало.

| Переменная | Значение | Зачем |
| --- | --- | --- |
| `NEXT_PUBLIC_YM_ENABLED` | `true` | Без этого счётчик не грузится (превью и локалка не пишут в боевой счётчик) |
| `NEXT_PUBLIC_YM_COUNTER_ID` | номер счётчика, напр. `98765432` | |
| `NEXT_PUBLIC_YM_REQUIRE_CONSENT` | `true` (по умолчанию) | `false` — грузить без согласия (модель уведомления) |
| `NEXT_PUBLIC_YM_WEBVISOR` | `true` (по умолчанию) | `false` — выключить Вебвизор |

### API — runtime

| Переменная | Значение | Зачем |
| --- | --- | --- |
| `YM_OFFLINE_ENABLED` | `true` | Включить выгрузку оплат в Метрику |
| `YM_COUNTER_ID` | тот же номер счётчика | Обязателен при `YM_OFFLINE_ENABLED=true` |
| `YM_OAUTH_TOKEN` | OAuth-токен (секрет) | Обязателен при `YM_OFFLINE_ENABLED=true`. В логах и ошибках маскируется |
| `YM_OFFLINE_GOAL` | `donation_paid` | Идентификатор цели «JavaScript-событие» |
| `YM_OFFLINE_INTERVAL_MINUTES` | `30` | Как часто выгружать очередь и опрашивать статусы |

API не стартует, если `YM_OFFLINE_ENABLED=true`, а номера или токена нет, — это лучше, чем молча
не выгружать.

## 3. OAuth-токен

1. Зайти под аккаунтом Яндекса, у которого есть **доступ на редактирование** к счётчику.
2. [oauth.yandex.ru](https://oauth.yandex.ru/) → «Создать приложение» → платформа «Веб-сервисы»
   (Redirect URI можно указать `https://oauth.yandex.ru/verification_code`).
3. Доступы Яндекс Метрики: **запись/загрузка данных** и **чтение статистики** (точные названия прав
   сверить в интерфейсе — они меняются).
4. Получить токен: `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID приложения>`.
5. Токен — **только** в переменную `YM_OAUTH_TOKEN` в Timeweb. В репозиторий, чаты, задачи — нельзя.

## 5. Как ведёт себя очередь при сбоях

- **Сбой записи в очередь не мешает оплате.** Строка `metrika_offline_conversion` пишется в той же
  транзакции, что переводит донат в `paid`, но внутри `SAVEPOINT metrika_enqueue`. Если INSERT
  падает, откатывается только точка сохранения: донат становится `paid`, в Метрику эта оплата не
  уйдёт, а в логах API появится `ERROR … Офлайн-конверсия доната <id> не записана, оплата проходит без неё`.
- **Зависшие выгрузки не крутятся вечно.** Строка, оставшаяся в `UPLOADING` дольше 15 минут
  (инстанс упал посреди выгрузки), возвращается в `PENDING` с засчитанной попыткой. Если это
  повторяется `MAX_UPLOAD_ATTEMPTS` (5) раз, строка становится `FAILED` с
  `last_error = 'Выгрузка прервана: инстанс не вернул строку из UPLOADING'`.
- **Параллельные проходы** (два инстанса API) не задваивают выгрузку: строки забираются
  `FOR UPDATE SKIP LOCKED`, внутри процесса стоит флаг `isRunning`.
- **Цели сайта до согласия на cookie** ждут в памяти вкладки и уходят после «Принять»
  (GOALS.md, «Правила»). Перезагрузка страницы до ответа на баннер их теряет, и это ожидаемо.

## 6. Проверка после деплоя

### Перенос в production, 07.11.2026

- Push в `production` по настройке проекта запускает Timeweb. Для этого переноса
  push требует отдельного согласования владельца из-за автоматического деплоя.
- При SPA-переходе в `/admin/**` вызывается `destruct`, отложенные вызовы до
  загрузки `tag.js` удаляются. При возврате на публичную страницу — новый `init` и `hit`.
- В upload и getUploading проверяются `source_quantity` (исходные строки),
  `line_quantity` (прошедшие валидацию) и число строк нашей пачки.
  [Контракт API](https://yandex.ru/dev/metrika/ru/management/openapi/offline_conversions/upload_1).
- При расхождении, отсутствии или некорректных количествах **вся пачка** переходит
  в `FAILED` с `uploading_id` и `last_error = acceptance_requires_review: ...`.
  В журнале — ERROR с количествами. Неизвестно, какие строки приняты: пачка не
  считается обработанной и не переотправляется. Не сбрасывать её в `PENDING`
  вслепую; сверить загрузку по ID и установить непринятые строки перед ручным
  восстановлением. `PROCESSED` означает обработку файла, не привязку всех строк к визитам.
- Тело HTTP-ошибки Яндекса и текст Prisma-ошибки в журнал не выводятся.
  SAVEPOINT охватывает чтение идентификаторов и INSERT outbox.
- В хиты уходят только нормализованные UTM и цифровой yclid из query;
  остальные query-параметры и query внешнего referrer обёртка не отправляет.

Следующие шаги требуют отдельного разрешения на боевую проверку. Текущая задача
не включает реальные платежи и события в боевой счётчик.

1. Открыть `https://mechetshamil.ru/?utm_source=test&utm_medium=check&_ym_debug=1` → «Принять» в баннере.
   В консоли браузера — отладочные сообщения Метрики, первый `hit` — с метками.
2. DevTools → Application → Cookies: `shamil_ft`, `shamil_lt` (наш учёт), `_ym_uid` (Метрика),
   `shamil_consent=granted`.
3. Пожертвовать 100 ₽ через форму. В базе у доната заполнены `last_utm_source = 'test'` и
   `ym_client_id`.
4. После оплаты — строка в `metrika_offline_conversion` в `PENDING`. Через ≤ `YM_OFFLINE_INTERVAL_MINUTES`
   — `UPLOADED` с `uploading_id`, затем `PROCESSED`. В логах API — «Загрузка N (CLIENT_ID): 1 строк…».
5. Через ~3 часа — конверсия `donation_paid` в отчётах Метрики (Отчёты → Конверсии) с ценностью в рублях.
6. Админка → «Источники»: строка `test / check` с суммой.

Состояние очереди:

```sql
SELECT status, skip_reason, count(*), max(last_error)
  FROM metrika_offline_conversion
 GROUP BY 1, 2;
```

`SKIPPED/no_identifier` — пожертвования без ClientID (отказ от cookie, блокировщик): это нормально,
они всё равно есть в нашем отчёте «Источники». `FAILED` с `401` — неверный или отозванный токен.
`FAILED` с «Выгрузка прервана…» — API падал посреди выгрузки (см. §5): смотреть логи перезапусков.
