# Форма пожертвования: разовая оплата и заглушка автоплатежа

Решение пользователя от 07.11.2026. База выпуска: origin/production,
4d2a46dcd00535b7afed97b1fe2f8fb341c3c577. Только компоненты формы и её адаптер;
дизайн остальных секций, админка, география, API и миграции не переносятся.

## Поведение

Главная открывает разовую форму. СБП, карта, SberPay, T-Pay и перевод по
реквизитам используют прежний POST /api/donations и прежний redirectUrl.
Конкретный онлайн-метод, как и раньше, выбирается на стороне Robokassa.
Сумма передаётся целыми копейками, сохраняются атрибуция, региональная ссылка,
анонимность, согласие и honeypot. Оплату подтверждает серверный callback.

«Автоплатёж» всегда доступен как переключатель. Он показывает только сообщение
«Регулярные пожертвования скоро появятся. Сейчас вы можете сделать разовое пожертвование»
и кнопку возврата. В этом режиме нет отправки формы, авторизации, выдачи кодов,
согласия на автоплатёж или создания подписки. Адаптер принимает только one_time,
не запрашивает доступность подписки и не зависит от recurring-capabilities API.

## Серверная граница и существующие подписки

В исходной production-версии нет recurring API/DTO/планировщика. Неизвестное поле
recurring отклоняется ValidationPipe с forbidNonWhitelisted до создания заказа.
Этот выпуск не добавляет такой функциональности и не меняет окружение API.
PAYMENT_RECURRING_ENABLED не включать. В локальном WIP с RecurringService значение
false приводит к checkoutSettings=null и серверному отказу создания подписки.
Защищённые WIP-маршруты управления, отмены, cookie и секретных кодов не удалены
и не заменены заглушкой; они не входят в этот выпуск. При будущем переносе API
сначала установить фактические подписки и сохранить управление и отмену при выключенном checkout.

## Будущий вход по email

В текущем API AuthService обслуживает сотрудников: email/пароль, JWT и refresh-сессии.
Почтового транспорта и OTP-входа донора в просмотренном коде нет. Управление
WIP-подпиской использует секретный код, а не подтверждённый email.
Сейчас новый auth-модуль, SMTP/API, отправка писем и СМС не добавляются.

Для следующего отдельного этапа:

1. Согласовать модель донора, связь с подпиской и переиспользование существующих
   сессий/защит. Не выдавать роли сотрудников донору и не связывать подписку
   только по введённому email.
2. Выделить почтовый транспорт внутри выбранной auth-архитектуры с выключенным
   состоянием по умолчанию. Ошибка доставки не должна означать успешный вход.
3. После отдельного разрешения настроить Yandex Cloud Postbox: отправителя/домен,
   необходимые DNS-записи, минимальные права и секреты в окружении сервера.
   Выбор SMTP/API и актуальные требования сверить с документацией провайдера.
4. Ввести криптографически случайные одноразовые коды с коротким сроком жизни,
   хешированным хранением, лимитами выдачи/проверки и атомарным погашением.
   Только успешная проверка кода подтверждает владение email и создаёт сессию.
   Не использовать универсальные коды и фиктивный успешный вход.
5. Отдельно проверить доставку, просроченный/повторный/неверный код, лимиты,
   восстановление доступа и миграцию владельцев подписок без потери отмены.
6. Регулярные платежи включать отдельным согласованным выпуском после готовности
   управления, условий и согласий, серверных ограничений, планировщика и проверки
   интеграции провайдера. Фискализацию, Receipt и СНО не добавлять.

## Демонстрация и выпуск

Отдельный worktree от production. Старый стенд 3406/3407 оставлен работающим.
Новый QA использует localhost:3416 и 127.0.0.1:3417, существующий кластер
PostgreSQL 127.0.0.1:22816 и свежую recurring_release_20261107_1228_test.
QA-обёртка меняет только имя тестовой БД и включает disabled-конфигурацию recurring;
защита непустой БД сохранена, исходящий доступ к провайдеру заблокирован.
Публичные витрины вне формы на этом ограниченном QA API используют fallback.
QA-скрипты, БД, логи, .env и временные файлы не публикуются.

По прямому указанию пользователя не запускаются lint, тесты, typecheck,
verify-recurring-browser, аудит, независимое ревью и новые скриншоты.
Показ формы не является проверкой реального платежа; заказы и списания не создаются.
Production-выпуск не требует новых миграций, переменных или настроек Robokassa.
Timeweb web 268991: production, /apps/web, npm run build, npm start.
Результат деплоя нужно подтвердить в Timeweb и просмотром публичной формы;
успешный push сам по себе его не доказывает. Откат формы — возврат web к базе выпуска.
