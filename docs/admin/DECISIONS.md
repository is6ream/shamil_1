# Решения, принятые в автономном режиме

Каждое решение обратимо. Пункты с пометкой **[проверить]** вынесены в REPORT.md → «Требует проверки человеком».

**D-01. Ветка от `chore/vercel-demo`, не от `main`.** Решение пользователя от 07.10.2026: в `main` нет
14 коммитов (лендинг v2, эмулятор Robokassa, оферта). Вливать в `main` по порядку: сначала
`chore/vercel-demo`, потом `feature/admin-panel`.

**D-02. Фикс `.gitignore`.** `build/` → `/build/` и `apps/*/build/`. Без этого `apps/web/components/build/`
не попадает в git. Это не новое поведение сайта, а починка репозитория.

**D-03. Колбэк с суммой, отличной от заказа, зачисляется по факту.** `OutSum` подписан паролем №2, значит сумма
подлинная. Отказ оставил бы списанные деньги без доната. Так задумано в CLAUDE.md («сумма и статус — из вебхука»).
**Пересмотрено 08.10.2026:** Telegram-оповещений нет (исключены из объёма). Вместо них расхождение пишется
`logger.warn` и системной записью `donation.amount_mismatch` в `audit_log` (`actor_type = system`,
`actor_label = webhook:<provider>`) — бухгалтер видит её в журнале админки. Запись делается после зачисления
и отдельно от него: сбой журнала не откатывает подтверждённые подписью деньги. Колбэк с неверной подписью —
`logger.warn` без ПДн, как и было. **[проверить]** — если нужно отклонять, это одна ветка в
`PaymentsService.applyWebhook`.

**D-04. Хеш паролей — `bcryptjs` (cost 12), не `argon2`.** Чистый JS: на reg.ru/ISPmanager нативная сборка
`argon2` может не встать. ТЗ разрешает bcrypt.

**D-05. Сессия админки.** Access JWT на 15 минут хранится в памяти вкладки и уходит в `Authorization: Bearer`.
Refresh-токен (случайные 32 байта, в БД только SHA-256) лежит в cookie `httpOnly; SameSite=Strict; Path=/api/admin/auth`,
`Secure` в production. При каждом обновлении токен ротируется. Повторное предъявление уже использованного
refresh-токена отзывает всё семейство (кража). CSRF: cookie шлётся только на `/api/admin/auth/*`, а
`refresh` возвращает токен в теле, которое чужой origin прочитать не может (CORS по списку).
Проверка сессии в layout `/admin` клиентская: данные админки на сервере Next не рендерятся, защита — на API.

**D-06. Права ролей.**

| Действие | SUPER_ADMIN | EDITOR | ACCOUNTANT |
| --- | --- | --- | --- |
| Контент, этапы, новости, медиа, видео | да | да | нет |
| Цель сбора и цель месяца | да | да | нет |
| Ручное поступление, подтверждение перевода | да | да | да |
| Список пожертвований, дашборд | да | да | да |
| ПДн жертвователей (имя для сверки, телефон) | да | нет (маска) | да |
| Экспорт CSV | да | нет | да |
| Журнал действий | да | нет | да |
| Пользователи админки | да | нет | нет |

Бухгалтер вносит ручные поступления: это его работа по выписке. По ТЗ заказчик (редактор) тоже должен
уметь внести наличные (DoD). **[проверить]**

**D-07. Старый статический токен сохранён.** `POST /admin/donations/:id/confirm` принимает либо JWT
с ролью, либо `ADMIN_API_TOKEN`. Скрипты и инструкции, написанные под токен, продолжают работать.

**D-08. Экспорт только CSV** (UTF-8 с BOM, разделитель `;` — так открывает русский Excel). XLSX потребовал бы
тяжёлую зависимость (`exceljs`). ТЗ формулирует «CSV/XLSX». **[проверить]**

**D-09. Заявок техподдержки нет.** Формы обратной связи на сайте нет. Добавлять её значило бы менять сайт
для посетителя, а это запрещено ограничениями. Шаг 9 сведён к health-check с проверкой БД.

**D-10. Хадисы и юридические тексты из админки не редактируются.** CLAUDE.md: хадисы только после выверки имамом.
Оферта — юридический документ.

**D-11. FAQ хранится, но на сайте не выводится.** Блока FAQ в макете нет. Новая секция — это изменение вида
сайта и работа дизайнера. Данные и API готовы, вывод — отдельная задача. **[проверить]**

**D-12. Новости.** Публикуются на `/novosti/[slug]` и списком на `/otchety`. Пока опубликованных нет, эти блоки
не рисуются и вид сайта не меняется. Предпросмотр черновика — в самой админке тем же компонентом.

**D-13. Видео не хостим.** Ссылки VK Видео / Rutube / YouTube по allowlist доменов превращаются в embed.
Видео из админки заменяет постер-заглушку в карточке «Видео с объекта». **[проверить]** формат embed VK
(`video_ext.php?oid=…&id=…`; для приватных роликов нужен `hash`).

**D-14. Ревалидация с `{ expire: 0 }`.** Заказчик должен сразу видеть правку на сайте (DoD). Профиль `max`
отдал бы один устаревший ответ.

**D-15. Хранилище S3 через `@aws-sdk/client-s3`, загружается лениво.** Протокол SigV4 руками не пишем.
SDK импортируется динамически только при `STORAGE_DRIVER=s3`. **[проверить]** на реальном бакете.

**D-16. Медиа отдаёт сам Nest** (`useStaticAssets`, префикс `/media/`). На reg.ru лучше отдавать каталог
веб-сервером — см. REPORT.md. Заголовок helmet `Cross-Origin-Resource-Policy` для `/media` ослаблен до
`cross-origin`: картинки грузятся с домена сайта.

**Пересмотрено 08.10.2026 (деплой на Timeweb Cloud App Platform):** диск контейнера эфемерен, поэтому в
production `STORAGE_DRIVER` — только `s3` (Timeweb S3); `local` в production роняет старт валидацией окружения.
В проде картинки отдаются по публичному адресу бакета `S3_PUBLIC_BASE_URL`, Nest их не раздаёт.
`useStaticAssets('/media')` подключается только при `local` (dev/test). Переменная `S3_PUBLIC_URL` переименована
в `S3_PUBLIC_BASE_URL`, добавлена `S3_FORCE_PATH_STYLE` (по умолчанию `true`).

## Решения бэкенда, сессия 08.10.2026

**D-17. Реквизиты счёта правит только SUPER_ADMIN.** D-06 относит реквизиты к контенту (SUPER_ADMIN, EDITOR),
но номер счёта — это то, куда уходят деньги: подмена из угнанной учётки редактора — прямой увод пожертвований.
Остальной контент редактор правит как раньше. Обратимо одной строкой (`REQUISITES_ROLES` в `auth/roles.ts`).
**[проверить]**

**D-18. `@nestjs/jwt` 11, а не 12.** Версия 12 — ESM-only и рассчитана на Nest 12; у нас Nest 11 и CommonJS,
Jest такой модуль не загружает. 11.0.2 — та же API, CJS, peer `@nestjs/common ^11`. Новых зависимостей нет —
это смена версии уже добавленной.

**D-19. `admin_user.token_version`.** Access-JWT несёт версию сессий пользователя, гард перечитывает пользователя
из БД на каждый запрос. Смена пароля, роли или деактивация увеличивают версию — старые access-токены
перестают приниматься сразу, а не через 15 минут. Роль всегда берётся из БД, не из токена. Аддитивная миграция.

**D-20. Коммиты без push.** CLAUDE.md требует спрашивать «Пушим в GitHub?» и не коммитить молча; промпт бэкенда
явно требует коммит после каждого шага. Коммиты делаются локально в `feature/admin-panel`, push — только
после ответа человека.

**D-21. Одинаковый ответ на все неудачи входа.** Нет пользователя, неверный пароль, блокировка, деактивация —
401 `Неверный e-mail или пароль`; bcrypt выполняется на каждой ветке (для несуществующего e-mail — с хешем-пустышкой).
О блокировке пользователь не узнаёт из ответа — иначе форма входа выдавала бы существование адреса.
Блокировка — 15 минут после 5 неудач, снимается сама или сбросом пароля суперадмином. **[проверить]**

**D-22. Пароли — от 12 символов, не длиннее 72 байт** (предел bcrypt; кириллица — 2 байта на букву). Фронт
предварительно взял 10 (D-F03) — контракт в API.md.

**D-23. Журнал `audit_log` — append-only триггером**, без внешних ключей на пользователей. Маскирование ПДн —
по закрытому списку имён полей (`audit/audit-snapshot.ts`), рекурсивно; e-mail пользователя админки разрешается
явно, e-mail жертвователя — нет.
