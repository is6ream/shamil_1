# Деплой фронтенда «Шамиль»

## Область и разрешения

Применять при сбоях публикации или несовпадении GitHub и публичного фронтенда. Ориентиры: GitHub `is6ream/shamil_1`, ветка `production`, Timeweb App Platform `shamil-web`, ID `268991`, домены `mechetshamil.ru` и `www.mechetshamil.ru`. Перед действием сверить их с заданием и текущей панелью; это ориентиры, а не доказательство актуальной конфигурации.

Прочитать [AGENTS.md](../../../AGENTS.md), [CLAUDE.md](../../../CLAUDE.md) и [инструкции фронтенда](../../../apps/web/AGENTS.md). При исправлении Next.js использовать локальный `shamil-nextjs`, если он установлен, включая документацию установленной версии. При подготовке выпуска применять локальный `shamil-release`, если он установлен. Эти соседние скиллы могут отсутствовать в клоне: тогда выполнять описанные здесь проверки, Git-процесс корневых инструкций и читать документацию Next.js из установленного пакета, разрешённого относительно apps/web. Отсутствие соседнего скилла не блокирует диагностику. Этот скилл уточняет диагностику фронтенда и не требует аудита всей инфраструктуры для исправления одного ассета.

По умолчанию выполнять диагностику без внешних изменений. Локальное исправление делать, если оно входит в запрос. Скилл сам по себе не разрешает commit/push, деплой, откат, перезапуск, изменение конфигурации или тарифа. Учитывать уже данное явное разрешение и его пределы; согласие на push при включённом автодеплое означает публикацию — заранее сообщить об этом. Не проводить платежи, не выводить секреты и содержимое переменных окружения.

## Сначала установить версию и стадию сбоя

- Зафиксировать время и часовой пояс проверки, локальный status, актуальный SHA целевой ветки GitHub, подключённый репозиторий/ветку, состояние автодеплоя, SHA выбранного деплоя и работающей версии Timeweb. Локальный remote-tracking ref без обновления не доказывает состояние GitHub.
- Использовать текущие GitHub и Timeweb через доступные инструменты или авторизованную панель. Приложенные логи дополняют их. Не обходить отсутствие доступа и не извлекать браузерные токены; назвать недоступные данные и предел вывода.
- Сопоставить попытку деплоя с SHA, временем начала/конца и статусом. Читать первичную ошибку выше итогового `Build failed`. Разделять установку зависимостей, `next build`, получение образа, `next start`, health-check и переключение трафика.
- Проверить предыдущий успешный деплой и текущую работающую версию: неудачная сборка может оставить старый контейнер. Не объявлять автоматический откат без свидетельств платформы. Сборка, push и healthy по отдельности не доказывают публикацию нужного SHA.
- Для health-check читать фактический путь и настройки фронтенда. Не подставлять API-маршрут `/api/health` как frontend health-check без проверки.

## Различать память, остановку процесса и ошибку сборки

Проверить лимит RAM, график за соответствующий период, доступные события платформы и логи сборки/запуска. Для каждого завершения установить команду, время, контейнер/деплой, если эти данные доступны.

`Killed` и exit code `137` допускают SIGKILL, но сами не подтверждают нехватку памяти. `SIGTERM` отдельно не считать OOM. Для подтверждения искать `OOMKilled`, события OOM ядра/платформы или счётчики cgroup с привязкой к нужному контейнеру и периоду. Точка графика ниже лимита не исключает короткого пика; текущие счётчики не доказывают причину старого сбоя. При отсутствии временных меток/SHA не приписывать общий лог конкретному деплою. Не увеличивать память предположительно.

## Проверить публичный результат и кеш

Сопоставить исходники целевого коммита с HTTP-ответами обоих доменов: HTML, подключённые ассеты и относящиеся к задаче metadata. Проверять статус, Content-Type и фактическое содержимое, а не только расширение или внешний вид вкладки.

При подозрении на старую версию выполнить несколько ограниченных серий GET с обычными URL, уникальным диагностическим query и `Cache-Control: no-cache`. Зафиксировать Date, Cache-Control, Age/ETag и доступные заголовки кеша. Query и no-cache не гарантируют обход всех уровней кеша. Сравнивать значимые ссылки и содержимое ассетов: динамический HTML может менять хеш без смены релиза. Проверить признаки разных экземпляров; конечная выборка не доказывает версию каждого экземпляра. Не очищать кеш и не перезапускать сервис ради диагностики без разрешения.

При проблемах с иконками проверить `favicon.ico`, `icon.png`, `apple-icon.png`, логотипы, manifest и объявления metadata там, где они существуют. Найти конфликтующие старые ссылки; проверить шапку, футер и мобильное меню по области задачи. Сохранить утверждённый знак, тему админки и остальное поведение. Версионировать URL только совместимым с установленным Next.js способом. Не обещать очистить кеш чужих браузеров, старых закладок, установленных ярлыков или внешних сервисов.

Известный пример, а не диагноз по умолчанию: при проверке 07.11.2026 сборка упала на `apps/web/app/favicon.ico` с `Format error decoding Ico: The PNG is not in RGBA format!` и кодом 1. В ICO был вложен RGB PNG. При такой ошибке проверить бинарный формат и пересоздать совместимый ICO с RGBA из согласованного исходника; подтвердить исправление production-сборкой. Это не свидетельство OOM.

## Минимальное исправление и выпуск

Сохранить существующий WIP; при смешанном diff использовать подходящий чистый checkout/worktree от актуальной целевой ветки. Не переносить рабочую директорию целиком. Проверить состав исправления, исключить секреты, временные файлы и `_to_delete/`.

Для изменения приложения выбрать проверки из AGENTS.md по области задачи. При исправлении сборки обязательно выполнить production build фронтенда: `npm run build --workspace @shamil/web` (команду сверить с package.json). Проверить воспроизводимость относительно целевого коммита, при необходимости локальный production-запуск и браузер desktop/mobile. Для чисто документальной правки достаточно проверки файлов, ссылок и diff.

Подготовить конкретный проверенный diff до запроса разрешения. Следовать Git-процессу CLAUDE.md: если согласования ещё нет, спросить «Пушим в GitHub?» и дождаться ответа. Без разрешения на публикацию закончить на локальном исправлении с явным статусом «production ещё не исправлен». Не задавать этот вопрос после одной диагностики без изменений.

После разрешённого выпуска проследить деплой нужного SHA до конечного статуса, затем проверить healthy, работающую версию, оба домена и целевые ассеты. Для UI проверить браузером desktop/mobile, для иконки вкладки — чистую сессию. Apple touch icon и manifest проверить как ресурсы; установку ярлыка на реальном устройстве не объявлять проверенной без устройства.

Если выпуск завершился ошибкой, прочитать новые логи и локализовать причину. Не повторять неизменённый деплой циклически. После одной неуспешной попытки повторную публикацию выполнять только после новой проверки причины и исправления, в пределах действующего разрешения. При недоступных доказательствах или необходимости неразрешённого действия остановить внешние изменения и сообщить конкретный блокер. Откат/изменение тарифа/настроек не считать подразумеваемым разрешением на push.

## Отчёт

Кратко указать: факты и предположения отдельно; SHA GitHub и работающей версии с источником; время/статус деплоя; первичную ошибку с отметками времени или строками; показатели памяти и наличие/отсутствие подтверждения OOM; результаты URL/браузера; минимальное действие или выполненное исправление; оставшиеся ограничения. После публикации завершать по проверенному результату на сайте, а не по успешному push.
